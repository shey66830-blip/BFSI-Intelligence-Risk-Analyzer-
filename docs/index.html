Context Guard How It Works

A consent-driven, privacy-aware intelligence layer that spots unusual transactions but never labels them as fraud. Instead it flags, correlates, explains, and lets a human decide.

No Fraud Labels Explainable Consent-Driven

01 What Context Guard Does

Context Guard sits between a transaction monitor and a human investigator. It does not replace either — it connects them.

🔍

Flags, not labels

Transactions are scored with an explainable risk score and a recommendation. The system never outputs "fraud" — it outputs "investigate" with reasons.

🏦

Asks the banks

When an anomaly is detected, Context Guard sends structured, consent-scoped requests to the relevant banks. Each bank searches its own records and returns structured findings — never raw customer data.

🔗

Correlates across banks

The system links bank reports to each other and to the transaction trail. Findings are labelled "corroborated" only when two independent sources agree.

📄

Drafts the report

An AI-drafted investigation report with confidence scores, citations, stated unknowns, and a clear disclaimer. An investigator reviews it and records a decision with their name and rationale.

02 Design Principles

PrincipleWhat it means in practice
No fraud labelsEvery output is a flag for investigation, a confidence score, and a recommendation — never a determination of guilt.
ExplainableEvery risk score has visible, auditable reasons. The report lists what it established, what it didn't, and how confident it is in each.
Consent-drivenAll data sharing requires active consent. The pipeline records the legal basis, retention period, and classification at every stage.
Bank-agnosticMock APIs are designed as drop-in replacements for real bank endpoints. The same case workflow and explainability layer carries over to production.
Privacy-awareNo bank sees another bank's data. Reports contain structured findings only — not raw customer records, device lists, or account numbers.

06 Data & Privacy

The demo uses fully synthetic data. The architecture is designed so that swapping in real bank APIs changes the data source without changing the pipeline.

No real data. Every transaction, entity, device, and bank response in this demo is generated from deterministic templates. The numbers look realistic — they are not real people's money.

Data flow during an investigation

  1. Transaction arrives — scored against the account's own baseline (leave-one-out, so an outlier can't hide inside its own mean)
  2. Gate decides — below 35%: routine. 35–65%: context request. Above 65%: full investigation.
  3. Request sent — structured, consent-scoped, with legal basis and retention policy attached
  4. Bank searches — each bank queries only its own records. No bank sees another bank's data.
  5. Reports returned — findings only, not raw customer data. Provenance envelope tracks what was asked and when.
  6. Correlation — system links reports to each other and to the transaction trail
  7. Report drafted — includes a "Data handling and consent" section documenting every disclosure

07 The 12-Stage Investigation Pipeline

This is the core of Context Guard. Every case moves through the same explicit stages. Each one records what it did and on what evidence.

Pipeline Flow
Transaction occurs
A new transaction is recorded at its originating bank. The system receives the transaction plus the account's recent history for context.
Initial AI analysis
Each transaction is scored against the account's own baseline using a leave-one-out method. Signals include velocity, amount deviation, geo inconsistency, device usage, structuring, crypto movement, and counterparty novelty. The account's aggregate activity is scored separately with a noisy-OR blend.
Meaningful anomaly or pattern?
The gate compares the aggregate score against the 35% threshold. This is the branch point.
NO — below 35%: Activity is consistent with the account's baseline. The gate closes. No bank is contacted. No case is opened. The trace explicitly records the stand-down.
YES — 35% or above: The pipeline continues. Between 35–65% it routes to the lighter "context verification" branch. Above 65% it routes to a full multi-bank investigation.
Investigation case created
A case is created with derived title, entity/bank scope, triggering transaction, and the reasons. Cases created by the pipeline are marked origin: "auto".
Relevant banks identified
The graph is expanded outward from the entity named on the case, then the banks are derived from the evidence trail rather than from a hardcoded list. Expansion follows two link types readable from the transaction record alone: a counterparty whose name resolves to a known entity, and a shared device used by another entity. It runs to two hops. In the coordinated scenario, one entity named on the case reaches two more and puts two banks in scope where the unexpanded case would have contacted one. Every entity added is stored on the case with the link that justified it, and the stage states the reasoning in plain language.
Investigation request sent
A structured, consent-scoped request goes to each bank. For the context branch, a lighter request with fewer fields is used. The request carries legal basis, retention policy, and data classification.
Simulated banks analyze their own data
Each bank searches only its own records. No bank sees another bank's transactions, customer list, or device data.
Structured reports returned
Banks answer with structured findings — not raw customer data. Every report carries a provenance envelope (request ID, timestamp, responding bank, disclosure note).
Context + cross-bank evidence correlation
Returned reports are linked to each other and to the transaction trail using 7 cross-referencing checks. Findings are labelled "corroborated" only when two independent sources agree.
AI-generated investigation report
Findings are drafted into an 8-section report with confidence scores, citations, stated unknowns, and a disclaimer. The drafter is template-based in the demo but has the same input/output contract as a production LLM call.
Risk assessment
Evidence is scored for escalation priority — as a flag, never a verdict. The assessment explicitly states it is "not a finding of wrongdoing."
Human / bank investigator decision
A named investigator reviews the report and records one of four decisions (close / request more context / continue investigation / escalate to compliance/FIU). The decision requires an investigator name and a written rationale. The system never decides alone.

08 The Anomaly Gate

The gate decides whether to open a case. It uses two thresholds to create three routes.

Score rangeRouteWhat happens
< 35% No action Gate closes. Nothing is shared. The trace records the stand-down with the score and reasons. No bank is ever contacted.
35–65% Context verification A consent-scoped context request goes to the bank holding the account. If the bank's response explains the anomaly, the score is adjusted downward. If it doesn't, the case escalates.
> 65% Investigation Full multi-bank investigation: formal requests, cross-bank correlation, report, and decision.
Why two thresholds? A $47,000 wire from a small-business account needs context — but it doesn't need three banks and a compliance referral. The context branch sends a lighter, consent-scoped request to the holding bank and adjusts the score based on what comes back. Only broad, multi-bank patterns trigger the full investigation path.

Context resolution

When the context branch is taken, the bank's response is checked for explanations and unresolved concerns:

  • Confirmations (each lowers the score): established relationship, KYC verified, active consent, matching invoice reference, etc.
  • Unresolved (each raises the score): the bank's internal risk rating is elevated, no matching business context found.

The adjusted score is shown in the report alongside the original, so the investigator can see how context changed the assessment.

09 Cross-Bank Evidence Correlation

This is where Context Guard's value is clearest: linking what each bank sees independently into a picture no single bank can see alone.

CheckWhat it looks forStrength
Shared counterpartiesA counterparty name appearing on transactions at multiple banksCorroborated (multi-bank)
Cross-bank entity referenceBank A names an entity whose transactions sit at Bank BCorroborated
Shared devicesA device ID disclosed independently by more than one bankCorroborated
Ownership linksBeneficial ownership flags or shared addresses disclosed by a bankSingle source
Fund return loopsValue sent from A to B and then back from B to ACorroborated if multi-bank
Endpoint convergenceMultiple senders sending value to the same sink (e.g., crypto exchange)Corroborated if multi-bank
Timing proximityTransfers at different banks within 60 minutes of each otherCorroborated
Corroborated vs single source. A finding is "corroborated" only when two independent banks provide evidence that supports it. "Single source" findings are included but clearly marked — they could be explained by information the system doesn't have.

10 The Investigation Report

The report is the product a human investigator reads. It has 8 sections, a disclaimer, and a citation list.

SectionPurpose
Executive summaryPlain-language overview of the pattern, how many banks are involved, and what can't be determined from the records.
What the evidence showsThe aggregated risk score and the signal types that contributed to it.
Cross-bank correlationEach finding with its ID, strength, source banks, and what it means.
Observed fund flowA chronological list of hops reconstructed from recorded counterparties, with timestamps and amounts.
Context returned by the bank(Context branch only) What the bank confirmed and what remains unresolved.
Confidence in this assessmentTwo dimensions — pattern confidence and intent confidence — with their basis.
What this report does not establishStated explicitly: unverified origins, unidentified end beneficiaries, single-bank-only accounts, unconfirmed device ownership, and the fundamental point that correlation is not intent.
Recommended next stepsActionable: confirm beneficial owners, request invoices, clarify end recipients, obtain statements before any adverse action.
The disclaimer. Every report ends with: "Context Guard flags and correlates for investigation. It does not determine that any person or business has committed an offence. Findings are indicators for a qualified human investigator to interpret, and the decision at stage 12 is theirs alone."

11 Confidence: Two Numbers, Not One

A single confidence number would be misleading. A well-corroborated pattern can coexist with a completely unexplained purpose — and that gap is where the real risk of over-reading lives.

Pattern confidence
87%
How well corroborated is the observed structure?

Can legitimately be high: the transfers happened, and two banks agree on them. This measures evidence integrity, not wrongdoing.

Intent confidence
20%
How well is the purpose understood?

Deliberately low when nothing explains the movement. Context verification (stage 6) is the only way to raise it — the system can't assume intent from structure alone.

Why this matters. If you report "95% confidence" on a pattern whose purpose nobody has established, you're implicitly telling the investigator that the pattern is almost certainly bad. But it might be legitimate trade. Splitting pattern from intent makes the uncertainty honest.

How the overall score is computed

overall = 0.6 × pattern + 0.4 × intent

Pattern confidence starts at 40% and adjusts based on: number of corroborated findings, whether multiple banks responded, the number of reconstructable hops, and consent verification. Intent confidence starts at 20% and adjusts based on contextual confirmations from the bank and unresolved concerns.

12 The Human Decision (Stage 12)

The pipeline never decides alone. Stage 12 requires a named investigator, a chosen action, and a written rationale.

DecisionWhat it meansResulting status
Close — activity explainedThe context or report explains the pattern. Record the rationale and close.closed
Request more contextHold the case open and ask the banks for the specific missing information.context_verification
Continue investigationKeep the case open for further analysis before any escalation.investigation
Escalate to compliance / FIURefer the case with the report attached. Escalation is a referral, not a finding of guilt.escalated
Validation. The system rejects decisions without a name or rationale (HTTP 400). It rejects decisions before a report exists (HTTP 409). It rejects invented verdicts like "declare fraud" — the only options are the four above. Every decision is recorded with the investigator's name, the rationale, and a timestamp.

14 Scoring Model

The aggregated activity score uses a noisy-OR blend so corroborating signals raise confidence while no single signal can ever reach certainty on its own.

How it works

Each signal type has a weight. Only distinct signal types contribute (duplicates are deduplicated, keeping the most severe instance). The survival probability is computed as:

survival = 1.0
for signal_type in distinct_types:
    survival *= (1.0 - SIGNAL_WEIGHTS[signal_type])
score = 1.0 - survival

This means:

  • No single signal reaches certainty — the maximum contribution is capped by the weight
  • Corroborating signals compound — two independent signals raise the score more than either alone
  • The output is a 0–1 score that maps to the three gate routes

Leave-one-out baseline

When scoring a transaction against the account's history, the baseline (mean and standard deviation) is computed without the transaction being tested. This prevents a single outlier from inflating its own baseline and hiding itself — a real bug that was caught and fixed during development.

15 Fund-Flow Path

The system reconstructs the observable chain of transfers from the counterparty names recorded on each transaction.

build_flow_path() produces:

  • hops — ordered list of from → to transfers with amounts, timestamps, and banks
  • sources — labels that appear only as senders (value entering the pattern)
  • sinks — labels that appear only as receivers (value leaving the pattern)
  • cycles — pairs (A, B) where A → B and B → A both exist (circular flow)
  • endpoint_totals — total value received by each sink
No private ledger access. The flow path is reconstructed from what each bank can already see on the transactions it processed. No bank's internal ledger is accessed or required.

17 Getting Started

Two terminals, no external services, no database setup.

One command

npm run install:web                          # first time only
pip install -r backend/requirements.txt      # first time only
npm run dev                                  # both servers, Ctrl-C stops both

Run this from the repository root. The backend is Flask (Python) and the frontend is Vite (Node) — two runtimes in two directories — so the launcher starts both and prefixes each log line with [api] or [web]. Typesetting npm run dev inside backend/ fails with ENOENT ... backend/package.json, because that directory holds no Node project.

Starting them separately

npm run dev:api     # cd backend && python app.py
npm run dev:web     # cd frontend && vite --host 127.0.0.1 --port 3000

Flask runs on http://localhost:5000 and seeds the demo dataset on first start if it is empty. Vite runs on http://127.0.0.1:3000 and proxies /api to Flask. Pass --host 127.0.0.1 explicitly — the default vite binds IPv6 only, so 127.0.0.1 fails without it.

Before a demo

npm run seed        # cd backend && python reset_demo.py

Restores the curated cases, the synthetic accounts and the default thresholds. Live ingests accumulate transactions, and each score is measured against the account's own baseline — so after the live feed has been clicked through a few times the coordinated scenario stops taking the investigation route. 19 Future Scope

The architecture is designed so that adding real capabilities does not require rewriting the pipeline.

🏦 Real bank APIs

Replace services/mock_banks.py with OAuth2-authenticated API calls. The case workflow, correlation logic, and report structure carry over unchanged.

🧠 Production LLM

Replace the template drafter with a real LLM call. The input (structured findings + confidence) and output (sectioned report) contract is identical.

🗄️ MongoDB at scale

In place: every case, trace, report, decision, evidence item, access request and audit entry persists in MongoDB, with indexes on the fields the queries actually use. What remains is operational — replica sets, migrations, retention and archival policy.

📊 Historical analytics

Track which signal types are most common, which contexts resolve anomalies, which decisions are taken — and feed that back into the scoring model.

🌐 Multi-jurisdiction

Add regulatory frameworks per jurisdiction. Different thresholds, different consent models, different escalation paths (SAR, STR, FIU referral).

🔄 Real-time streaming

Replace the demo's batch simulation with a streaming transaction feed. The pipeline stages execute on each incoming transaction, not just during demos.

21 Accounts & Roles

Context Guard is a system that asks people to make decisions about other people. So the first question it answers is who is allowed to see and do what.

There is a single login page for everyone. After signing in, what you can reach is decided by your role — not by a setting you can change in the browser. Four synthetic accounts are provisioned on first start (shown on the login page, one click to fill the form). They exist so the demo can be driven from every seat at the table.

👤

Analyst

Opens only the cases assigned to them. Customer identifiers arrive already masked, and the dashboard is a personal caseload rather than an organisation view. Can investigate a case and close it with a documented reason — but cannot escalate.

🔍

Compliance officer

Lands on a review queue: every open case, ranked by risk, with real identifiers. Holds the escalation decision, can assign cases to analysts, and can read the organisation-wide audit trail.

🛡️

Organisation admin

Gets the system overview plus the Administration section: create and suspend accounts, change roles, assign cases, tune the risk thresholds and privacy policy, and inspect every recorded action.

Sessions

Signing in mints an opaque token stored against the user in MongoDB; the browser sends it as a bearer token. Passwords are hashed with werkzeug, never stored or returned. Five failed attempts suspend the account. A role change, a suspension or a password reset revokes that user's existing sessions immediately — authority is re-read on every request, so a demotion takes effect on the next click, not the next login.

Three examples of the matrix doing real work:

  • Case scoping. Opening a case that is not yours returns 403 and writes an access_denied entry to the audit trail — a blocked attempt is itself evidence.
  • Escalation. The decision options are filtered per role, so an analyst sees three choices and a compliance officer sees four. The restricted option is refused server-side, not merely hidden.
  • Settings that bind. Raising the anomaly gate in Risk Settings genuinely changes the gate: at a 55% gate the hospital payment scores 38% and no case is opened at all.

23 Server-side Masking

Hiding a value in the interface is not privacy. The redaction happens before the response leaves the server.

An analyst's session is never sent the values it is not entitled to, so there is nothing to reveal with a browser console. Names become R. Kumar, counterparties and account numbers are redacted, and device identifiers are shortened to a stable handle. Each case response also declares what was withheld:

"privacy": {
  "level": "masked",
  "redacted_fields": ["counterparty", "device_id", "entity_name"],
  "note": "Identifiers masked for your role..."
}

Free text is part of the surface

Structured fields are the easy case. Case descriptions are prose — "Rajesh Kumar — ₹3,00,000 payment to Apollo Hospitals" — and would have leaked the very identifier the columns were hiding. So known entity names are replaced inside titles, descriptions and transaction text as well, before serialisation.

Attribution comes from the session

A decision used to record whatever name was typed into the form. It now records the authenticated identity, its user id and its role, alongside the rationale. The audit trail is the same idea: every sign-in, view, pipeline run, decision, settings change and refused request is written with the acting identity and can only be read back at the scope you hold.
